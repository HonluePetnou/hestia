Guide 03 · P4 IA / RAG · P1 pour l'évaluation

Le RAG : des réponses IA qui citent la NASA

Comment faire répondre un modèle de langage uniquement à partir de nos 36 rapports, avec des citations vérifiables — et un « je ne sais pas » quand il le faut.

Temps : ~3 hFichiers : backend/pipeline/*, app/services/*

1. Le principe en une image

Question ─► embedding ─► recherche pgvector (8 passages les plus proches)
                                   │
          ┌────────────────────────┘
          ▼
Prompt = consignes + passages numérotés [NTRS-ID, p.X] + question
          │
          ▼
LLM ─► réponse avec citations ─► vérification des citations ─► /ask → écran Assistant

LLM : modèle qui produit du texte ; il peut inventer (« halluciner »). RAG (Retrieval-Augmented Generation) : on lui fournit d'abord les bons passages et on lui interdit de sortir de ces sources. Le RAG réduit les erreurs mais ne les supprime pas : on vérifie.

2. Les embeddings et la similarité

Un embedding transforme un texte en un vecteur de nombres (ex. 1536 valeurs). Deux textes de sens proche ont des vecteurs proches. On mesure la proximité par la similarité cosinus (1 = même direction, 0 = sans rapport).

  • On calcule un vecteur pour chaque passage du corpus (une fois) et pour chaque question (à chaque appel).
  • Il faut le même modèle d'embedding pour le corpus et les questions.
  • La dimension du vecteur doit égaler EMBEDDING_DIM (colonne vector(1536)) : à choisir avant l'ingestion.

3. Découper le texte (chunking)

Implémenter chunk_pages() dans backend/pipeline/chunk.py :

  • Entrée : data/ntrs/text/<id>.jsonl (une ligne par page : {page, text}).
  • Passages d'environ 300 à 500 tokens (~1 200 à 2 000 caractères), avec un petit chevauchement (~50 tokens).
  • Ne jamais traverser une page : chaque passage garde un numéro de page exact → citation correcte.
  • Couper de préférence aux paragraphes ; ignorer les pages quasi vides (sommaire, pages blanches).
Astuce qui paie

Préfixer chaque passage par son contexte avant l'embedding : "[Titre du rapport — année — p.12] " + texte. Le passage devient plus facile à retrouver (idée de la « Contextual Retrieval » d'Anthropic).

4. Stocker et rechercher avec pgvector

La table chunks a déjà une colonne embedding vector(1536) et un index HNSW cosinus. L'opérateur <=> donne la distance cosinus (plus petit = plus proche) :

SELECT d.ntrs_id, d.title, c.page, c.content,
       1 - (c.embedding <=> :qvec) AS similarity
FROM chunks c JOIN documents d ON d.id = c.document_id
ORDER BY c.embedding <=> :qvec
LIMIT 8;

En SQLAlchemy : Chunk.embedding.cosine_distance(qvec) dans un order_by. C'est le TODO de app/services/retrieval.py.

5. Le prompt « sources seulement »

Système :
Tu es Hestia, assistant de sécurité incendie spatiale. Réponds UNIQUEMENT
avec les extraits fournis. Après chaque affirmation, cite la source au format
[NTRS-ID, p.X] exactement comme dans les extraits. Si les extraits ne
permettent pas de répondre, réponds : "Les sources indexées ne couvrent pas
cette question." N'invente ni chiffre ni conclusion. Rappelle les conditions
(matériau, O₂, pression, gravité) quand tu cites un résultat.

Utilisateur :
Extraits :
[20170000230, p.2] ... texte ...
[20210017787, p.6] ... texte ...
Question : How does flame spread change at lunar gravity?

6. Vérifier avant d'afficher

  1. Extraire toutes les citations de la réponse (regex \[([^\]]+?), p\.\s?(\d+)\]).
  2. Chaque citation doit correspondre à un passage fourni. Sinon : la retirer, ou passer insufficient_data = true.
  3. Si la meilleure similarité est trop basse (seuil à calibrer, ex. < 0,3) → ne pas appeler le LLM : répondre « données insuffisantes ».
  4. Renvoyer citations: [{ntrs_id, title, page, url}] → l'écran Assistant les affiche déjà.

7. Extraire les constats (findings) et le score Lune/Mars

Utiliser la sortie structurée (JSON imposé par un schéma) du fournisseur choisi, page par page ou rapport par rapport :

{"findings": [{"statement": "...", "experiment": "SAFFIRE", "page": 4,
               "relevance_moon": 0.0-1.0, "relevance_mars": 0.0-1.0,
               "confidence": 0.0-1.0, "rationale": "..."}]}
Le Guide d'équipe insiste : pas de score sans méthode

Le score doit suivre une grille écrite et affichée. Exemple : +0,3 si l'expérience porte sur des conditions proches de l'habitat (O₂ enrichi, pression réduite) ; +0,3 si l'effet dépend de la gravité ou de l'écoulement ; +0,2 si matériau de cabine ; +0,2 si résultat quantitatif. P1 relit le top 10 avant la démo. Le classement affiche « Pertinence × confiance » et la grille est consultable.

Le code gère déjà les trois via LLM_PROVIDER dans .env (app/services/llm.py). LLM_PROVIDER=mock permet de tout faire tourner sans clé — gardez-le comme plan B pour la démo.

9. Évaluer : le travail de P1 + P4

  • 10 questions-tests issues des fiches de lecture (guide 01), avec pour chacune la ou les sources attendues.
  • 3 questions hors corpus (ex. inflammation de la poussière de régolithe) → la bonne réponse est « données insuffisantes ».
  • Mesurer : source attendue retrouvée dans les 8 passages ? citations toutes valides ? affirmation fidèle au texte ?
  • Garder les résultats dans un tableau ; les montrer au jury est un vrai argument.

10. Ordre de travail conseillé

  1. Choisir fournisseur + EMBEDDING_DIM, mettre la clé dans .env.
  2. chunk.py testé sur 1 PDF → puis sur les 36.
  3. embed.py par lots (ex. 64 passages par appel), avec reprise en cas d'erreur de quota.
  4. ingest.py (sans --mock) : documents + chunks.
  5. retrieval.search() + /ask réel + vérification des citations.
  6. Extraction des findings + validation humaine + score affiché avec sa grille.
